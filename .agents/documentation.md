# Documentation

## Purpose and scope

Keep architecture, schema, releases, migrations, and recovery usable without tribal knowledge.

## Mandatory engineering requirements

Maintain the root README, architecture pages, database conventions, runbooks, and concise ADRs. Update
documentation in the same change as behavior. Include prerequisites, exact working directories,
environment variables, risks, verification, rollback/forward recovery, and ownership. Use fictional
Rwandan examples only.

## Forbidden patterns

No stale commands, undocumented public APIs, real customer details, credentials, copied vendor docs,
or claims that unexecuted validation passed.

## Correct example

An ADR records why generated Prisma sources are compiled into the package rather than generated by
`gym-api`.

## Common mistakes

Documenting only the happy path, omitting deployment order, or leaving migration caveats in chat.

## Review checklist

- Links and commands match current files and package scripts.
- Operational failure and recovery paths are present.
